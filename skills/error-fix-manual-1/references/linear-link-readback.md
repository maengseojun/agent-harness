# 사례 1 — Linear에 저장됐는데 링크 대조가 실패한 경우

2026-10-03 개인 작업에서 확인한 해결 과정이다. 사용자는 오랫동안 남은 링크 중복·표현 오류로 인식했다. 실제 탐색에서 확인한 직접 원인은 **일반 URL의 자동 링크 변환을 본문 변경으로 판단한 비교기**였다. 이 사례에서 실제 객체의 중복 생성은 확인하지 않았다. 아래 입력은 실제 변환 구조를 유지한 익명화 예시다.

## 실패 지점을 좁힌 순서

1. 실패 문구가 나온 작업의 원래 입력과 서비스 응답을 찾았다. 이전 설명만 보고 허용 조건을 넓히지 않았다.
2. 같은 개인 Linear 연결과 이슈를 별도로 조회했다. 목적지·제목·상태·본문이 존재함을 확인해, 저장 실패와 재조회 대조 실패를 분리했다.
3. 원래 입력의 일반 URL이 서비스에서 Markdown 자동 링크로 반환됨을 확인했다.
4. 저장 도구의 응답 해석부터 공통 본문 비교 함수까지 호출 경로를 따라갔다. 문자열·본문 표현 비교가 검증 실패와 작업 보류로 이어졌다.
5. 원본 입력과 원본 재조회 응답을 작은 재현으로 비교했다. 다른 URL·본문 변경이 거부되는지도 함께 검사했다.

원래 입력:

```text
관련 페이지: https://example.org/notes/result-1
```

서비스의 재조회 본문:

```text
관련 페이지: [https://example.org/notes/result-1](<https://example.org/notes/result-1>)
```

표시 글자와 실제 목적지가 같은 하나의 링크다. 본문에 URL이 두 번 보인다는 사실은 객체가 두 개 생성됐다는 증거가 아니다. 반면 아래 링크는 같다고 처리하면 안 된다.

```text
관련 페이지: [https://example.org/notes/result-1](https://example.org/notes/result-2)
```

## 공통 함수에서 수정한 경계

서비스가 만든 동일 URL의 일반 표기·꺾쇠 자동 링크·자기 URL을 표시명으로 쓰는 Markdown 링크를 비교할 수 있게 했다. 임의 표시명과 임의 주소를 전부 제거하는 방식은 쓰지 않았다. 다른 목적지와 변경·누락된 본문은 거부했다. 기존 워크스페이스·이슈 ID·관계·사용자 승인 검증은 유지했다.

직전에는 목록 기호의 표현 차이도 확인됐다. 따라서 URL 변환만 따로 성공시키는 대신 기존 비교 규칙과의 회귀를 확인했다. 목록의 하이픈과 별표를 같은 기호로 볼 수 있어도 체크 상태나 코드 안의 기호까지 바꾸어서는 안 된다.

독립 검토에서 URL 허용만 추가하면 코드 내부의 내용 변경까지 통과할 수 있음이 드러났다. 실제 보완은 다음 순서로 진행됐다.

- 변하지 않은 코드가 있다는 이유로 주변 일반 문장의 URL 변환도 실패하는 경우를 수정했다.
- 여러 줄 인라인 코드와 서로 다른 길이의 백틱이 섞인 내용을 보호했다.
- 종료 기호가 더 긴 코드 블록, 끝까지 종료하지 않은 코드 블록, CRLF 줄바꿈을 다뤘다.
- 인용문 안의 코드와 목록 안의 코드 블록은 보수적으로 원문 대조를 유지했다. 전체 Markdown 동등성을 보장하려는 수정으로 넓히지 않았다.

검토가 새로운 결함을 찾을 때마다 실제 재현을 보존했다. 적용 중인 수정 횟수 제한에 도달했을 때는 미완성 설치를 하지 않고 사유와 보완안을 제시했다. 사용자가 추가 수정·검증을 승인한 뒤 그 범위만 이어갔다. 이 사례가 모든 오류마다 동일한 승인 단계를 요구하는 규칙은 아니다.

## 설치 이후에도 확인한 것

관련 도구 검사 54개와 설치 검사 20개가 통과했고, 검토 소스와 설치 파일 9개가 일치했다. 이 수치는 이 사례의 당시 결과이며 이 매뉴얼의 고정 검사 수가 아니다.

설치 직후 새 훅은 `modified`였고, 현재 대화의 자동 검증은 이전 실패 결과를 계속 반환했다. 새 비교기를 별도로 실행하면 실제 본문은 통과했으므로 **소스 수정 성공과 실제 실행 적용 성공이 다른 단계**임을 확인했다.

앱에서 사용자가 새 훅을 승인한 후 도구·작업 기록 실행 설정 7개가 모두 `trusted`로 조회됐다. 그다음 이전에 실패한 쓰기의 실제 재조회가 `verified` 영수증으로 전환됐다. 새로운 일반 URL을 포함한 허용된 갱신과 별도 재조회도 통과했다. 마지막에 다른 검토자가 설치 일치·신뢰 상태·실제 응답과 영수증을 확인했다.

## 이 사례가 증명한 범위

확인한 링크 표현 오류와 해당 실행 경로의 수정·설치·실제 적용을 증명했다. 모든 Work·클라우드 시작·종료 경로, 과거 실패 영수증 전체 정리, Notion 저장을 증명한 것은 아니다. 공개·공유 매뉴얼에는 실제 개인 URL·워크스페이스·이슈 UUID·대화 ID·원본 전체 로그를 넣지 않았다.

다른 서비스에 적용할 때도 먼저 같은 목적지의 원본 입력과 실제 재조회에서 변환이 관측되는지 확인한다. 예를 들어 Notion URL 별칭, 인코딩, 질의 문자열 차이를 이 Linear 사례만으로 같은 주소라고 추측하지 않는다.
