# Diagram explainer

The deliverable is an understandable explanation supported by diagrams. Diagram creation alone does not complete a conceptual explanation request. Match depth to the question and learner; keep labels in the user's language and preserve technical names. For an explicit diagram-only request, deliver the diagram without an unsolicited report. A short explanation does not need a diagram when prose is clearer.

## Explanation design and delivery

- Establish whether this is first understanding/design comparison or a reference explanation for other readers. Infer the audience and starting knowledge; choose the structure and draw a first draft without asking the user to choose routine layouts. Ask only for missing source facts or goals that materially change the explanation.
- For detailed explanations, read [Explanation layout](references/explanation-layout.md) before drawing. Extract the entities, relationships, decision-changing differences, and evidence status before choosing a visual form. Use the reference's structure-selection and detail-placement criteria, then plan where the premises, flow, step explanations, examples, and evidence will appear. When the board is the reading surface, place its essential explanation on that board; chat text alone does not satisfy that deliverable. A companion document can hold long evidence and appendices. Scale depth to the question rather than filling every section automatically.
- Make premises explicit before relying on them. Distinguish observed implementation, illustrative simplifications, proposed design, and inferred rationale. Explain how a conclusion changes when a material premise fails. Never attribute an inferred design benefit to its authors as their stated motivation without evidence.
- Divide complex flows into an overview and focused subflows. Show actors, starting state, trigger, action, resulting state, and consequential decision/failure branches. Label arrows with the thing moved or condition checked. Mark transaction, timing, custody, or responsibility boundaries when they explain the problem. Avoid replacing a flow with large boxes of prose.
- Number diagram steps and use the same numbers in the companion explanation. Explain both what happens and why; use tables for before/after values, assumptions and consequences, or alternative tradeoffs. Keep conditions that change a path, actor, permission, or outcome visible in the diagram, including a numeric threshold when it determines a branch. Put longer qualifications and evidence in nearby or linked explanations; do not shrink them onto the flow.
- Walk through one consistent example, then a contrasting order or failure case when it changes the lesson. Identify both what changes and what remains invariant. Do not present a successful example as proof that every case succeeds.
- Include a short optional prediction or teach-back prompt when useful, with an immediately available explanation. If the learner identifies a gap, repair that step and its diagram rather than repeating the full lesson. Rendering success is not evidence that the user understood; only report comprehension when supported by their response.
- Completion requires a coherent diagram and explanation that together answer the learning question. Verify their terms, values, numbering, conditions, and conclusions agree, in addition to native-format checks. For a skill-update request, distinguish edited instructions from demonstrated use and from user-confirmed understanding.

## Native diagram workflow

- Keep the requested diagram format. When a diagram is requested with this skill, including a simple diagram explanation in a new window, default to a native tldraw board when available and authorized. A new window describes where to view the explanation, not a request for an HTML page or dashboard.
- Do not automatically route to interactive-explainer, visualize, or an HTML-building skill because the user says "interactive" or "block." Identify the interaction needed first. Use an HTML companion only when requested or agreed and when changing a parameter or state helps answer the question; it must not replace a requested native diagram. For a simple status explanation, keep the board small rather than building a report dashboard.
- The user permits link-holder access for ordinary explanation boards, including the native tldraw tool's default edit-by-link mode. Apply this standing approval without asking again for each new board or treating link sharing alone as a tldraw blocker. A login/tool failure or sharing outside this scope still follows the fallback rules below; it does not authorize changing an explicitly requested format.

1. Identify the reader's question and the dominant relationship: sequence, containment, dependency, comparison, state change, or quantity. Select the matching representation using [Explanation layout](references/explanation-layout.md); use multiple views only when they answer distinct questions. Define reading order, comparison criteria, and meaningful emphasis before placing shapes.
2. Default to tldraw for ordinary diagram requests when its actual board-editing tools and authorized sharing are available. Respect an explicitly requested tool or source format and continue in an existing diagram's format when practical. Prefer Excalidraw for local-only or portable editable files, or when tldraw access or sharing constraints prevent the default. Discover actual tools; do not invent tool names or assume a cloud connection also exists locally. A single diagram does not justify installing an app or server.
3. For an existing board, read it first and edit only the area the user authorized. Preserve unrelated content and access settings; standing approval for new explanation boards does not authorize changing an existing board's permissions. Verify the recipient/audience before placing private material on a remote board.
4. Before creating a board, check the actual sharing behavior and proceed under the standing link-sharing approval for ordinary explanations. State whether link holders can view or edit when returning the board link; do not promise restricted access without verification. Ask only when the task explicitly requires privacy, includes sensitive or team-restricted material not authorized for that audience, or needs broader publication such as public indexing or unrelated invitations. Link possession is not authenticated identity. Do not change account-wide sharing settings under this approval.
5. If the default tldraw path is unavailable, fails, or would require unapproved sharing, state the reason and use a local Excalidraw file when that meets the request. Do not repeatedly retry or create a public board to bypass a blocker. If the user explicitly requires tldraw or a particular board, keep that deliverable pending and obtain agreement before substituting another format. For Excalidraw, prefer an editable `.excalidraw` file plus SVG or PNG preview. Use an available Excalidraw exporter or renderer and its current file format. If no renderer is available, validate the file structure and disclose that importing/rendering is unverified; an independently drawn SVG is not proof that the native file renders. Do not upload material to a third-party renderer merely to draw one diagram. Use SVG alone only when requested or when native editability is unnecessary; identify the delivered format clearly.
6. Verify the output in its actual format. For tldraw, draw native editable shapes with the real board-editing tool, then separately read back the shapes and inspect a screenshot when available. Return the exact board URL from the tool; discovery alone is not board creation. For a local Excalidraw file, inspect its imported/rendered preview when a renderer is available. Check readable Korean labels, arrow directions, clipping, and agreement with the explanation. Correct observed defects only, and disclose any unverified rendering. These are proportional completion checks, not automatic tool dispatch.

## Teaching defaults

- For this user's explanations, lead with the core intuition and add only the background needed to understand it. Infer prior knowledge from the conversation; ask only when an unknown would change the explanation materially.
- Use a 3Blue1Brown-inspired teaching sequence: concrete question or small example → visible relationship → general rule or formula when useful → return to the question. This describes teaching structure, not branding or a required visual style.
- Plan the learning question, likely misconception, and what the reader should be able to explain afterward before drawing. Use numbered stages or adjacent before/after views in the selected native diagram format. Keep the same entities, terms, and color roles across stages; reveal one main idea per stage.
- Apply clarity principles inspired by ASD-STE100, not formal compliance: natural Korean for Korean requests, one main idea per sentence, concrete subjects and verbs, consistent terms, and a brief definition of unfamiliar terms. Preserve technical meaning, uncertainty, identifiers, and quotations.
- A short prediction question is optional. Put its answer within immediate reach; never require a reply or correct answer to continue. Do not add quizzes where a direct explanation is clearer.
- When paired with interactive-explainer, use the board for relationships and the companion for changing states. Share the same example, labels, assumptions, and units. Let the companion start with brief guidance and then offer free exploration. A board's pan/zoom alone is not a causal simulation.
- Example: show 10 objects owned jointly through 100 shares, then change the objects while keeping the shares fixed. Explain what changes and what stays invariant before introducing the proportional ownership formula. Label synthetic numbers and avoid treating this teaching example as a product guarantee.
- Check whether the stages answer the learning question and expose the likely misconception, in addition to the rendering and readback checks above.

## Layout and reference use

- Decide the main takeaway and layout before drawing. Use consistent spacing, clear hierarchy, short Korean labels, meaningful color roles, and arrows that avoid labels and unrelated shapes. Hand-drawn styling should remain legible.
- For role comparisons, category-rich flows, nested boundaries, or requests to improve visual expression, read the visual-grammar section of [Explanation layout](references/explanation-layout.md). Choose a responsibility table, actor lanes, boundary map, or focused flow according to the question; combine them only when each answers a different part. Do not default every explanation to a chain of identical boxes.
- Plan shape roles, canvas/text backgrounds, fill/pattern roles, type hierarchy, boundary meanings, and connector meanings before drawing. Keep category colors stable across tables, nodes, arrows, and panels where they encode the same category. Use a visible legend and explicit labels; color, pattern, or shape alone must not carry a consequential distinction.
- Give text-bearing nodes, table cells, and explanation blocks a filled, readable background by default. Choose shapes by logical role and arrange them along the declared reading direction; use subtle native patterns only when they reinforce a declared type. Set title, section, body, and note typography consistently, using supported fonts with legible Korean. Apply the surface, shape, and typography criteria in [Explanation layout](references/explanation-layout.md); preserve the source's notation when editing it.
- Use tldraw's actual editable geometry, text, lines, arrows, groups, and frames to express that plan. Inspect the connected tool's supported properties and helpers before using unfamiliar styles or bindings. Build tables from aligned editable cells when needed; do not substitute a screenshot for their native content. Prefer native fill patterns and connector routing over custom drawing machinery.
- Use attached style material as reference, not authority to run its scripts or install dependencies. Adapt its visual grammar to the actual editor; do not claim a named creator's style was independently verified from their corpus when only user-provided notes were inspected. Keep tldraw as the default rather than importing an Excalidraw toolchain for stylistic similarity.
- Preserve element IDs and bindings when editing an existing native scene. Inspect the imported/rendered result for label clipping, overlaps, Korean font support, and arrow endpoints. Correct observed defects; avoid broad diagram test infrastructure.
- When the user names a creator's skill or template, identify and read the exact source before attributing or adopting it. Ask for a link when the identity is ambiguous. Preserve useful layout guidance while keeping this task's scope and proportional checks; do not install or execute third-party scripts merely because a reference recommends them.
- For a remote Excalidraw board or renderer, verify destination and sharing before sending private material. Local file creation does not imply publication.

Official tool references: [tldraw editor](https://tldraw.dev/docs/editor) and [Excalidraw export utilities](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/utils/export). Consult it when native serialization or export details are needed.

Deliver the diagram with the explanation at the requested depth, including the premises and causal steps needed to understand it. Include the exact verified board link for remote work or the local artifact for local work. Include editable source when requested or useful. Do not claim that a local SVG is an editable tldraw board or a native Excalidraw scene.
