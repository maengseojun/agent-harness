# Middleman code questions

A Middleman is **a code-level question the existing pages and code do not answer.** It is the user's personal Linear convention. Read the applicable pages and code before opening one. Ordinary prerequisites, research, authentication failures and connection errors keep their own meaning.

- One shared Middleman has one canonical issue, linked to every consuming task with native `blocks`/`blockedBy`. Independent work keeps its own Spec/Plan, Owns and lead; a small question may stay inside the consuming Plan.
- Kind is the verified label `Middleman` (resolve the real id in the workspace; never infer Kind from a word in the title). If the label is unavailable, keep a pending-sync note and report the gap. A dependency relation alone does not make a Middleman.
- Read the actual answer before the dependent step and reflect it in the Spec/Plan. A question does not authorize changing Architecture/Rules or marking any task Done. Do not open a second issue just to rename one.

Template for the issue or Plan item:

- Kind: Middleman
- Question: the unresolved code decision and why the pages do not answer it
- Sources: checked pages and code, applicable Spec/Plan
- Owner / scope: decision owner, Owns, permitted work
- Blocks: consuming task ids and relations
- Choices: options, constraints, tradeoffs
- Expected answer / evidence
- Resolution / next action: pending or answered, evidence, consuming Spec/Plan update

In a Notion outcome, the corresponding section is **Middleman decisions** (question, sources, answer, reasoning, effect on tasks). Record an unanswered question as pending, never as decided. Omit the section when empty.
