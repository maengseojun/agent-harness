# Project/task workflow (canonical contract)

Used by harness-run, task-brief, execute-code-brief and prepare-work-deliverable. Reuses Linear documents, relations and Obsidian notes; it adds no database, bot or lock.

- **Project:** use interviews and source research to agree Architecture, then Environment & Rules, then decompose into tasks, each with its own Spec and Plan. Architecture is the top entry: goal and success criteria, structure and responsibilities, decisions with reasons (`D-n`), open questions, links to Rules and Tasks. Each task links to its Architecture section.
- **After task creation,** the lead reads the task, Spec/Plan and relevant Architecture/Rules to find prerequisite work and unresolved code questions. Use a Middleman only for a code-level question the pages do not answer; other prerequisites are ordinary tasks or Plan items. Read actual results before the dependent step. Independent steps may continue. Incorporate answers within agreed Architecture/Rules and return material findings to the upper decision.
- **Spec/Plan:** Spec holds goal, `must_haves`, Owns, requirements, `AC-n`, exclusions and unresolved inputs. Plan holds readiness, environment, steps, `Verification` (check per `AC-n`), failure/change handling and review focus. Map every requirement to a task and a check; missing ownership or verification means not ready. Standalone short tasks keep their own Spec/Plan without project hierarchy. Trivial edits need no scaffolding.
- **Status:** documents are `draft`, `current` or `superseded`. Record each source's document id, fetched `updatedAt` and the user's approval reference in its header and in the execution record. A draft is not an execution criterion. Agreement on documents and authorization to execute are separate; record the requested scope.
- **Before execution or resumption:** task current state, then linked Spec/Plan, then Architecture/Rules, then dependency results. Check revision, readiness, inputs and Owns against the request. Resolve conflicting or stale criteria before affected work. Keep the task body useful: goal, phase, decision reason, blocker, next action, links, artifacts, check results. Put settled decisions into the canonical documents, not only comments.
- **Plan changes:** small changes within Owns (order, file choice) may proceed with a log of previous/new approach, reason and impact. Changes to goal, architecture, scope, constraints or Acceptance need re-agreement first; a Plan change cannot widen Owns.
- **One lead per task.** Handoff keeps the task id and records outgoing/incoming lead, applied document revisions, progress, artifacts, checks, blockers, next action. Parallel tasks need a compare of Owns and dependencies first.
- **Connection failure:** try safe reads and reconnection first. Offline work may use only previously fetched and approved criteria; keep a local pending-sync note and disclose the gap. Do not start a new task on unread criteria. After recovery, fetch current sources and reconcile before retrying; never retry an uncertain write blindly.
- **Done:** after Acceptance and required review, record evidence, limitations and links, then close the task yourself. Passing tests, Stop or a merged PR alone are not Done; Acceptance, required review and recorded evidence are. The user never manages Linear (MAE-216 decision). A Notion record is a separate step (closeout flow in SKILL.md).
