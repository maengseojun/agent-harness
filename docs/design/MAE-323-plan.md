Linear: MAE-323. Date: 2026-11-06. Language: Korean, the text the user approved; the sub-plan of each bundle is written in English like the other plans here.

상태: 사용자가 완료 기준을 승인했다(2026-11-06, "승인"). 이 파일이 기준 문서다. 초안과 리뷰 기록은 볼트의 `wiki/drafts/DRAFT-MAE-323-plan.md`, `wiki/reviews/REV-MAE-323-20261105-plan.md`에 있다. 결정 D-1~D-9와 파트 지도는 정해졌다. 이 문서는 상위 계획이다. 묶음마다 하위 Plan과 Sub-tasks 표를 따로 쓴다. 이 작업은 트랙 1이다. 트랙 2(결과물의 질, 마무리 이해 확인, 개선 절차)는 MAE-324다.

## Spec

Goal: 좋은 하네스의 기준표([[DRAFT-MAE-323-good-harness]]) 중 G3(효율)와 G4(역할 수행)를 고친다. 조사-계획-실행-검증 루프에서 낭비되는 대기 시간을 줄이고, 테스트 통과와 리뷰 통과의 의미를 분명히 한다. G5(개선 가능성)는 측정 스크립트와 변경 감지까지 다룬다. G1(결과물의 질)은 다루지 않는다. MAE-324가 다룬다.

Deliverable: 묶음 3개의 PR, 적용 전후 측정 리포트, 갱신된 harness-run 규칙.

### Assumptions

- A-1 메인 세션의 모델과 effort는 사용자가 직접 정한다. 이번 패치는 바꾸지 않는다.
- A-2 조사 에이전트의 동시 실행 수는 제한하지 않는다.
- A-3 eta 하네스는 범위 밖이다. eta 체크아웃에서도 쓰이는 maeng 코드는 eta 동작을 바꾸지 않는다. 공유 에이전트 정의 4개(`maeng-tools/agents`)는 eta에서도 쓰이므로 고치지 않는다. effort와 도구 제한은 개인 세계에서만 적용한다. eta까지 넓히는 것은 사용자의 지시가 있을 때 한다.
- A-4 G1 게이트(기본 브랜치 푸시 금지, `maeng-ship` 머지)는 유지한다. 머지 게이트는 오류 때 닫힌다.
- A-5 흐름: 계획자가 아키텍처, 큰 계획, 과제 분배를 한다. Astra가 전체 계획을 리뷰한다. 그다음 Sonnet, Haiku, Sol, Decisions가 등급에 맞게 실행한다. 계획자와 리뷰어는 자기 세션에서 위임할 수 있다.
- A-6 계획자는 세션 모델이다. Opus이거나 Fable이다. 규칙은 "Opus 세션"이 아니라 "계획자"로 적는다.
- A-7 D-7과 D-8의 해석: 2회 뒤 high 이상이 남으면 고치고, 그 수정과 남은 high만 보는 확인 실행을 1회 돌린다. 확인 실행은 새 지적을 올리지 않는다. 확인 실행이 남은 high를 닫지 못하면 CEO 브리프에 넣어 `승인 #N`을 요청한다. 상한이 지적을 승인하는 것은 아니다. 브리프는 `승인 #N`이 실패한 코드 리뷰를 대신한다고 적는다.

Owns: `plugins/maeng-tools/agents/**`, `plugins/maeng-harness/skills/{harness-run,task-brief,execute-code-brief}/**`, `plugins/maeng-harness/bin/{maeng-review,maeng-ship,maeng-verify}`, `plugins/maeng-harness/hooks/hooks.json`, `plugins/maeng-harness/schemas/verdict.schema.json`, `plugins/maeng-harness/policy/roles.json`(새 파일), `plugins/maeng-harness/lib/maeng/{evidence,handlers,tree,gates,receipts}.py`, `plugins/maeng-harness/tests/**`, `.maeng/verify.json`, `.github/workflows/**`, `tools/testperf/**`, `tools/watch/**`(새 폴더).

Exclusions: 요청 난이도 점수기와 판정 모델(자동 라우터), 훅 성능 개선, 시작 컨텍스트 전체 축소(플랫폼 영역), 조사 에이전트 동시성 제한, eta 하네스, Decisions 배선 변경, 메인 세션의 직접 편집 금지, 수리 상한 변경, 쓰기 범위 겹침의 코드 거부.

must_haves:
- T1 위임되는 모든 에이전트의 모델과 effort가 역할 표에서 정해진다.
- T2 작업 중에는 영향 범위 테스트가 기본으로 돈다.
- T3 전체 테스트는 브랜치당 두 번을 기본으로 한다(1라운드 전, 2라운드 전). 안전을 위한 재실행은 막지 않는다.
- T4 통과 증거가 무엇을 증명하고 무엇을 증명하지 않는지 규칙에 적혀 있다.
- T5 큰 작업의 계획은 코드 전에 독립 리뷰를 받을 수 있다(계획 종류). 받지 않은 큰 작업에는 알림이 나온다. 강제하지 않는다.
- T6 리뷰는 2회와 확인 실행 1회 안에 끝나고, 막는 지적의 뜻이 적혀 있다.
- A1 측정 스크립트가 저장소에 있고 기준값을 재현한다.
- K1 Plan의 Sub-tasks 표의 등급 -> 역할 표 -> 위임 호출의 model과 effort.

## 역할 표와 등급 표 (`policy/roles.json`의 내용)

역할:

| 역할 | 모델 | 기본 effort | 허용 범위 | 대기 |
|---|---|---|---|---|
| 계획자 | 세션 모델(Opus 또는 Fable) | Opus xhigh, Fable high | Opus high~max, Fable medium~xhigh | 없음 |
| 계획 리뷰 | Astra | high | medium~xhigh | Opus xhigh, Fable high 순서 |
| 하위 PR 리뷰 | Sol | xhigh | 현행 | Opus high, Fable high 순서 |
| 작은 작업 리뷰 | Sol | high | 현행 | Opus high, Fable high 순서 |
| 통합 리뷰 | Fable | high | medium~xhigh | Astra high, Opus high 순서 |
| 문서 리뷰(`docs`) | Astra | medium | 현행 | Opus high |
| 조사 리뷰(`research`) | Sol | xhigh | 현행 | Opus high |
| Notion 리뷰(`notion`) | Sol | medium | 현행 | Opus high |
| 전체 감사 | Fable | high | 사용자 요청 시만 | 없음 |

리뷰어를 고르는 규칙(코드가 적용한다):
1. 후보는 "모델" 칸, 그다음 "대기" 칸의 순서다.
2. 그 변경을 실제로 쓴 모델과 같은 후보는 건너뛴다. 작성 모델은 실제 실행자를 기록한 값이다. 대기 모델이 구현했으면 그 모델이다. 지금의 `--author codex` 규칙을 일반화한 것이다.
3. 계획 리뷰와 통합 리뷰에서는 계획자의 모델과 같은 후보도 건너뛴다. 하위 PR, 작은 작업, 문서, 조사, Notion 리뷰에는 이 제외가 없다. 지금 동작과 같다.
4. 다음 후보로 넘어가는 조건은 2, 3의 제외와 가용성 실패뿐이다.
5. 남은 후보가 없으면 리뷰를 돌리지 않고 `blocked`로 보고한다.
예: 계획자가 Fable이면 통합 리뷰는 Astra high다. 계획자가 Opus이고 Sol이 쓴 하위 PR이면 리뷰는 Opus high다.

Opus가 리뷰어일 때의 effort는 D-1의 범위(high~max) 안에 둔다. 그래서 지금의 Opus medium 대기 2개(하위 PR, Notion)를 high로 올린다.

실행 등급(Sub-tasks 표의 `등급` 열 값):

| 등급 | 모델 | effort | 상한 | 대기 | 쓰는 곳 |
|---|---|---|---|---|---|
| quick | Haiku | medium | high | 없음 | 조사, 정확한 작은 수정 |
| standard | Sonnet | medium | high | Sol medium | 과제 한 개 구현 |
| deep | Sonnet | high | xhigh | Sol high | 분기, 계산, 보안이 있는 구현 |
| design | Opus(`architect`) | high | xhigh | 없음 | 하위 설계, 내부 리뷰 |

규칙:
- 값은 시작값이다. 묶음 1의 측정으로 조정한다.
- 기본값은 고정한다. 과제 표가 없는 작은 작업은 1단계 내린다. 올림은 계획자가 이유를 Revisions에 적어 명시한다.
- 실패에 따라 effort를 자동으로 올리지 않는다. 실패하면 브리프를 고친다(기존 Keep/Change/Scope).
- 대기 모델로 넘어가는 조건은 가용성 실패뿐이다: 사용량 한도, 제공자 거부, 서버 오류. 테스트 실패나 리뷰 fail은 조건이 아니다. 넘어가면 `fallback_from`을 남긴다.
- 리뷰어 선택은 위의 "리뷰어를 고르는 규칙"을 따른다.
- Fable은 실행(구현, 조사, 기록)에 쓰지 않는다.
- 표의 모든 행은 `sourceUrl`과 `verifiedAt`을 가진다. 30일이 지난 확인은 낡은 것으로 표시한다.
- 표에 없는 값이 필요한 과제만 행에 모델과 effort를 직접 적는다.

### P2 테스트 실행 구조 (묶음 1과 2)
1. 묶음 1: Plan 기본 문구와 `verify.json`의 ship check를 `python3 -m pytest -q -n 8`로 바꾼다. 94초 기준으로 약 4시간이 여기서 줄어든다.
2. 묶음 2: `impact.py run`을 작업 중의 기본 검사로 연결한다. 기본 Python에서 돌게 하고(`coverage`, 지도 자동 생성), 선택 실행 3건의 rc 5 실패를 고친다. 선택이 실패하면 전체 실행으로 돌아간다.
3. 묶음 2: 리뷰 진입 조건은 바꾸지 않는다. `maeng-review`는 지금처럼 매 라운드 ship-verified(최종 트리의 전체 검사)를 요구한다. 영향 범위 검사는 작업 중의 도구이고 게이트 증거가 아니다. `impact.py run`의 결과는 ship-verified를 만들지 못한다.
   - D-3의 순서: 전체 1회 -> 1라운드 리뷰 -> 수정하는 동안은 영향 범위 -> 수정이 끝난 head에서 전체 1회 -> 2라운드 리뷰 -> 머지. 2라운드가 pass면 "머지 전 전체"와 "2라운드 진입 전 전체"는 같은 실행이다. 2라운드 뒤에 high가 남아 확인 실행(D-8)을 하면, 수정한 head에서 전체를 1회 더 돌리고 그것이 머지 전 전체다. AC-5는 이 재실행을 따로 센다.
   - 1라운드가 pass면 전체 검사는 1회다. base가 움직이면 지금 규칙대로 다시 검증한다.
4. 묶음 2: 테스트를 gate(PR을 막음)와 periodic(주기 실행) 2단으로 나눈다. 표본 변이는 periodic이다.
5. 묶음 2: CI 워크플로가 모든 플러그인의 테스트를 돌리고 집계 검사 하나를 낸다. 정보용이다. 먼저 테스트가 실제 HOME과 키 없이 도는지 확인한다.
6. 묶음 3: 2주 뒤 `maeng-ship`이 집계 검사를 읽을지 판단한다. 필수로 바꾸는 조건과 되돌리는 조건을 규칙에 적는다.

### P3 테스트 신뢰 규칙 (묶음 2)
1. AC에서 기대값을 끌어낸 테스트를 기본으로 한다. Plan의 `Fails-if`에 음성 경로(null, 빈 값, 음수, 예외)를 의무로 적는다.
2. 버그 수정은 실패 재현을 먼저 남긴다.
3. 증거 등급을 규칙에 적는다: 하네스가 실행한 러너 > 선언 > 에이전트 보고. `declared` 증거가 러너 증거를 대신하지 못하는 범위도 적는다.
4. 같은 트리에서 성공과 실패가 모두 나오면 flaky로 기록한다.
5. 영어 문장을 테스트로 고정하지 않는다. 코드가 읽는 값만 고정한다.
6. 시험: 추가한 테스트를 base 코드에서 돌려 실패하는지 확인한다. 결과는 정보용이다. 표본 변이와 검출을 비교한다.

### P4 게이트 (묶음 1과 2)
1. P4a, 묶음 1: 다른 세션의 변경 때문에 코드를 고치지 않은 세션이 막히는 오탐을 고친다(MAE-232와 같은 현상).
2. P4b: Stop 훅은 UNVERIFIED와 UNRECORDED를 알리기만 한다. 차단하지 않는다. Stop 훅의 오류와 시간 초과는 통과시킨다.
   - 알림은 모델이 읽어야 한다. `systemMessage`는 사용자에게만 보일 수 있다. 다음 프롬프트의 맥락으로 넣는 방식(기존 `context_out`)을 먼저 실험한다.
   - dots가 읽는 상태값을 다시 정한다. 지금은 차단되지 않은 첫 정지에 누락이 있으면 `running`으로 적는다(`handlers.py` 593-594행). 차단이 없어지면 끝난 실행이 `running`으로 남는다.
3. P4b: PR 생성에는 게이트를 더하지 않는다. 같은 검증을 이미 리뷰 진입(`maeng-review`)과 머지(`maeng-ship` 57-59행)가 강제한다. `gh pr create` 뒤의 기존 알림(`handlers.py` 464-465행)을 넓혀 미검증과 미기록을 알린다. D-2의 "PR 직전 또는 알림" 중 알림을 고른 것이다. 새 차단 지점을 만들지 않는다.
4. P4b: 기록 누락은 어떤 차단도 만들지 않는다. 알림은 PR당 1회다.
5. P4b의 대안(알림이 약하다고 측정되면): 실행당 1회만 차단.

### P5 서브에이전트 맥락 (묶음 1과 2)
1. 묶음 1: 스킬 설명 합계의 크기 테스트를 넣는다. 현재 값 20,693바이트를 상한으로 고정한다. 줄이는 일은 이후에 한다.
2. 묶음 2: P1-3의 개인 흐름용 정의를 기본으로 쓴다. general-purpose는 기본으로 쓰지 않는다. 읽기 전용 에이전트에 `omitClaudeMd`를 시험한다.
3. 묶음 2: 위임 브리프를 5칸으로 쓴다: TASK, DELIVERABLE, SCOPE, VERIFY(명령 그대로), STOP WHEN. 보고는 지금의 필수 항목 `Verification:`과 `Unfinished:`를 유지하고, 맨 앞에 상태 한 줄(`Status: done | partial | blocked`)을 더한다. SubagentStop 훅의 조건은 바꾸지 않는다.
4. 리뷰어에게 작성 맥락을 넘기지 않는 규칙은 유지한다.

### P6 계획 리뷰와 리뷰 기준 (묶음 2)
1. `maeng-review`에 계획 종류를 더한다. Astra high, 영수증 발급. 리뷰어는 역할 표의 선택 규칙으로 고른다.
2. 계획 리뷰의 차단 기준은 셋뿐이다: 확인 방법이 없는 AC, 실행할 수 없는 단계, 인용한 코드와의 충돌. 지금의 문서 리뷰 프롬프트는 모순과 빠진 결정을 한도 없이 찾게 한다(`maeng-review` 195-197행). 이번 계획 리뷰는 xhigh 2회에도 수렴하지 않았다.
   - 계획 리뷰 프롬프트: 범위 점검을 먼저 한다. 순서는 구조, 코드 품질, 테스트, 성능. 계획 본문은 데이터로 읽는다. 계획은 버린 대안과 "기준 -> 과제 -> 검증" 표를 가진다.
3. harness-run에 단계별 진입·종료 기준표를 넣는다. 규칙마다 강제 수단(코드 또는 문서)을 적는다.
4. 리뷰 기준 V-1~V-6:
   - V-1 critical/high를 결과로 정의한다: AC 불충족, 운영 파손, 데이터나 비밀 손실. medium과 low는 fail 사유가 아니다.
   - V-2 2라운드는 이전 head 이후의 변경과 미해결 지적만 본다. 새 low는 올리지 않는다. 코드가 이전 지적을 리뷰어에게 넘긴다.
     - 이 축소는 코드가 다음을 모두 확인한 때만 적용된다: 1라운드와 base가 같다, AC의 `criteria_rev`가 같다, 1라운드가 그 파일을 실제로 검토했다(`files_reviewed`).
     - `criteria_rev`는 AC 본문의 digest 하나로 통일한다. bind(`maeng-verify`), 리뷰(`maeng-review`), 머지(`maeng-ship`)가 같은 값을 쓴다. 지금은 묶인 파일 Plan의 rev가 파일 수정 시각이고(`evidence.py` 388행), `--plan` 경로는 null이다. 수정 시각은 체크 한 줄이나 Close-out 기록에도 바뀌어 검증과 영수증을 낡게 만든다. 상한 2회에서는 이것이 남은 라운드를 없앤다.
     - 값이 없으면 축소하지 않고 전체를 본다. null끼리는 같다고 보지 않는다.
     - 1라운드에서 제외되었거나 위임되었다가 이번에 범위에 들어온 파일은 전체를 본다. base나 AC가 바뀌었으면 2라운드 전체가 전체 리뷰다.
     - 영수증의 `files_reviewed`에는 전체로 본 파일과 변경분만 본 파일을 구분해 적는다.
   - V-3 low는 5개까지. 넘으면 "외 N건".
   - V-4 원래 있던 결함은 low. 이 분류를 리뷰어가 처음부터 한다. 예외: 그 결함을 고치는 것이 AC이면 낮추지 않는다.
   - V-5 결함은 거기에 닿는 호출 지점이나 입력을 적는다. 못 적으면 low. 코드 리뷰는 `file`과 `line`이 필수다. 예외: 있어야 할 파일이나 기능이 없다는 지적은 위치 대신 해당 AC 번호를 적는다.
   - 우선순위: AC 미충족은 항상 차단 사유다. V-4와 V-5의 하향은 AC 미충족에 적용하지 않는다.
   - V-6 "AC에 대해 반증을 시도한다"는 유지하고 "지적 없음은 유효한 결과"를 더한다.
5. `--max-rounds`의 기본값을 2로 바꾼다(D-7). 2회 뒤의 확인 실행을 더한다(D-8): 남은 high 이상과 그 수정 diff만 본다. 새 지적은 올리지 않는다. PR당 1회뿐이다. 상한은 실행이 아니라 리뷰된 head를 센다. 같은 head의 재실행, `blocked` 판정, 범위 분할은 세지 않는다. 확인 실행이 남은 high를 모두 닫았다고 판정하면 그 head의 pass 영수증을 낸다. `maeng-ship`은 이 영수증으로 머지한다. 닫지 못하면 fail이고 A-7의 `승인 #N` 경로로 간다.
6. 안전장치: 저장된 과거 리뷰를 새 프롬프트로 다시 돌려, 이번 diff가 만든 critical/high가 사라지지 않는지 확인한다. 묶음을 재구성할 수 있는지는 미정이다(OQ-2).

### P8 변경 감지와 주기 개선 (묶음 3)
1. 주간 작업이 변경 채널과 폐기 일정을 확인해 Linear 추적 이슈 하나를 갱신하고 Slack으로 알린다. 보고만 한다. 역할 표를 고치지 않는다.
2. 검증된 CLI 버전을 기록한다. 실행 버전이 다르면 한 줄로 알리고 훅 스모크와 전체 테스트를 돌린다.
3. 모델 온보딩 절차 문서: 응답 확인, 공식 문서 확인, 후보 행 추가, 고정 과제 한 쌍 비교, 사용자 승인 뒤 교체.
4. MAE-324로 옮겼다(부품 목록, "있을 때와 없을 때"의 한 쌍 측정).

### P9 큰 작업의 계획 리뷰 알림 (묶음 2)
1. "큰 작업"을 코드로 판정한다: 하위 이슈가 있거나 Sub-tasks 표가 2행 이상.
2. 큰 작업에 유효한 계획 영수증이 없으면 PR 생성 뒤와 코드 리뷰 진입에서 한 줄로 알린다. 리뷰 진입도 머지도 막지 않는다.
3. 계획 영수증은 계획 리뷰(P6-1)의 pass 기록이다. AC 본문의 digest(`criteria_rev`, P6의 V-2)에 묶는다. AC 본문이 바뀌면 영수증은 낡은 것이고, 알림이 다시 나온다. 트리에는 묶지 않는다.
4. Plan의 Sub-tasks 표에 등급 열이 없으면 standard로 보고 한 줄로 알린다. 거부하지 않는다.
5. 머지 강제는 넣지 않는다. 이유: 영수증 규칙이 약하다. base를 호출자가 주고, 코드를 먼저 쓴 작업은 영수증을 얻지 못한다(Astra 2회차, Fable 감사). 계획 리뷰가 없는 큰 작업의 리뷰 fail이 더 많다고 측정되면 다시 본다.
