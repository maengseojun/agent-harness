# MAE-323 설계 설명: gates 파트

이 문서는 설계 인터뷰의 자료다. 파트의 경로는 `plugins/maeng-harness/lib/maeng/handlers.py`다. 이 파트의 질문은 "어디서 막는가"다.

## 지금의 동작

- Stop 훅은 턴이 끝날 때마다 두 조건으로 막는다. UNVERIFIED: 코드가 바뀌었는데 검증 증거가 없다. UNRECORDED: 마지막 변경 뒤의 기록이 없다.
- 같은 턴의 두 번째 정지는 차단하지 않고 메시지로 낮춘다.
- 다른 세션이 같은 저장소의 코드를 바꾸면, 코드를 고치지 않은 세션도 막힌다. 오탐이다.
- `gh pr create` 뒤에는 "리뷰를 돌려라"는 알림이 나온다.
- dots가 읽는 상태 파일은, 차단되지 않은 첫 정지에 누락이 있으면 `running`으로 적는다.
- 강제 지점은 따로 있다. `maeng-review`는 검증되지 않은 head의 리뷰를 거부한다. `maeng-ship merge`는 검증과 pass 영수증 없이는 머지를 거부한다. 기본 브랜치로의 직접 push는 막힌다(G1).

## 바꾸는 것

1. 오탐을 고친다. 코드를 고치지 않은 세션은 막히지 않고, 알림도 받지 않는다(묶음 1).
2. Stop 훅은 UNVERIFIED와 UNRECORDED를 알리기만 한다. 차단하지 않는다. Stop 훅의 오류와 시간 초과는 통과시킨다(묶음 2).
3. 알림은 모델이 읽어야 한다. 다음 프롬프트의 맥락으로 넣는 방식을 먼저 실험한다.
4. 상태 파일의 값을 다시 정한다. 끝난 실행이 `running`으로 남지 않게 한다.
5. PR 생성 뒤의 알림을 넓힌다. 미검증, 미기록, 큰 작업의 계획 영수증 없음을 알린다. PR 생성은 막지 않는다.
6. 기록의 누락은 어떤 차단도 만들지 않는다. 알림은 PR당 1회다.

## 바꾸지 않는 것

- 리뷰 진입과 머지의 강제. G1 게이트. 머지 게이트는 오류 때 닫힌다.

## 왜 이렇게 하는가

- 주 99회의 Stop 차단이 대기를 만들었다. 그중 일부는 오탐이다. 처음 측정은 164회였다. 재개된 세션 파일에 같은 사건이 복사돼 있어 중복으로 센 값이었다(2026-11-06 정정).
- 검증이 정말로 필요한 지점은 코드가 다른 사람에게 가는 때다: 리뷰와 머지. 그 두 곳은 이미 막는다. 턴마다 막는 것은 같은 검사를 더 일찍, 더 자주 하는 것이다.
- 사용자의 결정(D-2): "PR 직전 또는 알림이 나아보이긴 하네". 둘 중 알림을 골랐다. 새 차단 지점을 만들지 않기 위해서다.
- Stop 훅은 안전장치가 아니라 알림이므로 오류 때 열려야 한다. 머지 게이트는 안전장치이므로 오류 때 닫혀야 한다.

## 버린 대안

- PR 생성에 게이트를 더하기. 같은 검증이 리뷰 진입과 머지에 이미 있다. 차단 지점만 하나 늘어난다.
- 지금처럼 턴마다 막기.
- 남긴 대안: 알림이 약하다고 측정되면 실행당 1회만 막는다.

## 깨지는 때

- 알림이 사용자에게만 보이고 모델에게 닿지 않을 때. 모델은 검증 없이 계속 일한다. 리뷰 진입에서 처음 막히고, 그때 한꺼번에 고치게 된다.
- 차단이 없어진 뒤 상태값을 고치지 않으면, dots가 끝난 실행을 실행 중으로 읽는다.
- 기록이 줄어들 때. 기록의 누락은 이제 아무것도 막지 않는다. PR당 1회의 알림에 기댄다.
- 측정에서 머지 뒤 수정 커밋이 늘어나면 이 변경을 되돌린다.
