# MAE-323 설계 설명: 전체

이 문서는 설계 인터뷰의 자료다. 계획은 `docs/design/MAE-323-plan.md`에 있다.

## 무엇을 하는가

개인 하네스의 작업 루프(조사, 계획, 실행, 검증)를 고친다. PR 3개로 나눈다.

1. 묶음 1, 설정과 측정. 서브에이전트의 모델과 effort를 표 한 곳에서 정한다. 전체 테스트를 8개 프로세스로 나눠 돌린다. 측정 스크립트를 저장소에 둔다.
2. 묶음 2, 구조. Stop 훅은 막지 않고 알린다. 리뷰는 2회와 확인 실행 1회로 끝낸다. 막는 지적의 뜻을 적는다. 작업 중에는 영향 범위 테스트를 돌린다. 계획 리뷰 종류를 더한다.
3. 묶음 3, 변경 감지. 주간 점검이 모델과 CLI의 변경을 알린다.

## 왜 하는가

최근 7일의 측정이 근거다.

- 서브에이전트 활동의 92%가 xhigh 이상이었다. 위임 호출 156건 중 effort를 지정한 것은 1건이다.
- 전체 테스트가 107회, 6.8시간 돌았다. 브랜치당 약 4회다. 영향 범위 도구의 사용은 0회다.
- Stop 훅이 164회 막았다.
- 리뷰의 pass 비율은 34%다. PR 26개 중 12개가 4회 이상 리뷰를 받았다.
- 표본 변이 20개 중 9개만 테스트가 잡았다.

사용자의 기준표로는 G3(효율)와 G4(역할 수행)에 해당한다. G1(결과물의 질)은 이 작업이 다루지 않는다. MAE-324가 다룬다.

## 주요 결정, 버린 대안, 깨지는 때

### 1. 모델과 effort는 `policy/roles.json` 한 곳에 둔다
- 이유: 지금은 같은 짝이 5곳에 따로 적혀 있다. 한 곳을 고치면 나머지가 어긋난다.
- 버린 대안: 훅으로 effort를 채우기. 지금의 플러그인 훅은 Agent 호출에 등록돼 있지 않고, 거부나 통과만 한다. 플랫폼 문서에는 훅이 입력을 고쳐 쓰는 기능이 있다. 그러나 effort를 그렇게 넣는 것이 통하는지는 문서에 없다. 에이전트 정의 파일에 effort를 적는 방식은 문서에 있다. 그래서 정의 파일을 골랐다. 요청 난이도를 재는 자동 라우터도 뺐다. 참고한 저장소 어디에도 효과 수치가 없다.
- 깨지는 때: CLI가 에이전트 정의의 effort를 무시할 때. 그래서 묶음 1은 먼저 실험으로 확인한다. 표가 낡을 때. 그래서 행마다 출처와 확인 날짜를 적는다.

### 2. 실패해도 effort를 자동으로 올리지 않는다
- 이유: 실패의 원인은 대개 브리프다. 실패하면 브리프를 고친다.
- 대기 모델로 넘어가는 조건은 가용성 실패뿐이다: 사용량 한도, 제공자 거부, 서버 오류.
- 깨지는 때: 과제가 정말로 더 높은 effort를 필요로 할 때. 이때는 계획자가 이유를 적고 직접 올린다.

### 3. Stop 훅은 막지 않고 알린다
- 이유: 턴마다 막는 것이 주 164회의 대기를 만들었다. 같은 검증을 리뷰 진입(`maeng-review`)과 머지(`maeng-ship`)가 이미 강제한다.
- 버린 대안: PR 생성 때 막기. 새 차단 지점이 생긴다. 남긴 대안: 알림이 약하다고 측정되면 실행당 1회만 막는다.
- 깨지는 때: 알림이 모델에게 닿지 않을 때. 미검증 작업이 리뷰 직전까지 쌓일 때.

### 4. 전체 테스트는 리뷰 라운드 앞에서만 돌린다
- 순서: 전체 1회, 1라운드 리뷰, 수정하는 동안은 영향 범위, 수정이 끝난 head에서 전체 1회, 2라운드 리뷰, 머지.
- 영향 범위 테스트의 결과는 게이트 증거가 아니다. 리뷰 진입은 지금처럼 최종 트리의 전체 검사를 요구한다.
- 깨지는 때: 영향 선택이 관련 테스트를 놓칠 때. 그 실패는 라운드 앞의 전체 실행이 잡는다. 선택이 실패하면 전체 실행으로 돌아간다.

### 5. 리뷰는 2회와 확인 실행 1회다
- 이유: PR #45는 28회를 돌고도 수렴하지 않았다. 리뷰어는 "변경이 틀렸다"에서 시작하고, 막는 지적의 정의가 없었다.
- 막는 지적은 결과로 정의한다: 완료 기준 불충족, 운영 파손, 데이터나 비밀의 손실. medium과 low는 fail 사유가 아니다.
- 2회 뒤 high가 남으면 고친다. 그 수정과 남은 high만 보는 확인 실행을 1회 돌린다. 닫히면 그 head의 pass 영수증이 나온다. 닫히지 않으면 사용자의 `승인 #N`으로 간다.
- 버린 대안: 4회 유지. 2회에서 끝내고 확인 없이 머지하기. 이 경우 마지막 수정이 리뷰 없이 들어간다.
- 깨지는 때: 진짜 결함이 low로 낮춰질 때. 그래서 저장된 과거 리뷰를 새 프롬프트로 다시 돌려, 막는 지적이 사라지지 않는지 본다. 완료 기준의 불충족은 어떤 경우에도 낮추지 않는다.

### 6. 계획 리뷰는 종류를 더하되 강제하지 않는다
- 이유: 리뷰 fail의 주된 경로가 완료 기준의 불충족이었다. 계획을 먼저 보면 줄어든다.
- 강제하지 않는 이유: 영수증 규칙이 약하다. 코드를 먼저 쓴 작업은 영수증을 얻지 못한다. 큰 작업에 영수증이 없으면 알림만 낸다.
- 깨지는 때: 알림이 무시될 때. 측정으로 다시 본다.

### 7. eta를 건드리지 않는다
- 공유 에이전트 정의 4개는 eta에서도 쓰인다. 고치지 않는다. 개인 흐름용 정의를 새로 더한다.

### 8. 순서
- 묶음 1이 먼저다. 작고 되돌리기 쉽다. 측정 스크립트가 있어야 나머지의 효과를 잴 수 있다.
- 파트는 커밋으로 나눈다. 측정에서 나빠진 파트는 그 커밋을 되돌린다.

## 되돌리는 조건

- 머지 뒤 수정 커밋이 늘어난다: Stop 알림 전환이나 리뷰 기준을 되돌린다.
- 영향 선택이 전체 실행에서 잡히는 실패를 놓친다: 영향 선택을 되돌린다.
- 2회 상한에서 `승인 #N` 요청이 지금의 "4회 이상 PR" 비율보다 많아진다: 리뷰 기준을 다시 본다.
