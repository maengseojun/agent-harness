# MAE-323 설계 설명: evidence 파트

이 문서는 설계 인터뷰의 자료다. 파트의 경로는 `plugins/maeng-harness/lib/maeng/evidence.py`와 `plugins/maeng-harness/bin/maeng-review`다. 이 파트의 질문은 "무엇이 증거인가"다.

## 지금의 동작

- 검증 증거는 작업 트리에 묶인다. 트리가 바뀌면 증거는 낡은 것이 된다.
- `maeng-review`는 매 라운드 ship-verified를 요구한다. 최종 트리에서 필요한 검사가 모두 통과했고 모든 완료 기준이 충족이라는 뜻이다.
- 리뷰의 모델과 effort는 `maeng-review` 안의 상수다.
- 라운드 상한은 4다. 저장된 실행의 수를 센다. head의 수가 아니다. `blocked` 판정과 범위 분할도 횟수를 쓴다.
- 이전 라운드의 지적은 리뷰어에게 가지 않는다.
- 완료 기준의 판(`criteria_rev`)은 묶인 Plan 파일의 수정 시각이다. `--plan`으로 준 경로에서는 값이 없다.
- pass의 조건은 "critical과 high가 없고 모든 완료 기준 충족"이다. 등급의 뜻은 적혀 있지 않다.

## 바꾸는 것

1. 모델과 effort를 `policy/roles.json`에서 읽는다. 코드의 상수는 없앤다.
2. 리뷰어를 고르는 규칙을 코드에 넣는다.
   - 그 변경을 실제로 쓴 모델과 같은 후보는 건너뛴다.
   - 계획 리뷰와 통합 리뷰에서는 계획자의 모델과 같은 후보도 건너뛴다.
   - 다음 후보로 넘어가는 조건은 이 제외와 가용성 실패뿐이다.
   - 남은 후보가 없으면 리뷰를 돌리지 않고 `blocked`로 보고한다.
3. `criteria_rev`를 완료 기준 본문의 digest 하나로 통일한다. bind, 리뷰, 머지가 같은 값을 쓴다.
4. 리뷰 기준 V-1~V-6을 프롬프트와 스키마에 넣는다. 코드 리뷰의 지적은 파일과 줄이 필수다.
5. 2라운드는 이전 head 이후의 변경과 미해결 지적만 본다. 조건이 있다: 1라운드와 base가 같다, `criteria_rev`가 같다, 1라운드가 그 파일을 실제로 검토했다. 하나라도 아니면 전체를 본다. 값이 없으면 같다고 보지 않는다.
6. 라운드 상한을 2로 한다. 상한은 리뷰된 head를 센다. 같은 head의 재실행과 `blocked` 판정은 세지 않는다.
7. 2회 뒤 확인 실행을 PR당 1회 둔다. 남은 high와 그 수정 diff만 본다. 새 지적은 올리지 않는다. 닫혔으면 그 head의 pass 영수증을 낸다.
8. 계획 종류를 더한다. Astra high가 본다. 영수증은 완료 기준 본문의 digest에 묶는다.
9. 영향 범위 테스트의 결과는 ship-verified를 만들지 못한다.

## 왜 이렇게 하는가

- 수정 시각은 체크 한 줄이나 기록 한 줄에도 바뀐다. 그러면 검증과 영수증이 이유 없이 낡은 것이 된다. 상한이 2회이면 이것이 남은 라운드를 없앤다. 본문의 digest는 기준의 글이 바뀔 때만 바뀐다.
- 번호는 같고 문구만 바뀐 완료 기준도 digest가 잡는다.
- 상한이 실행을 세면 `blocked` 판정이나 재실행이 라운드를 쓴다. head를 세면 "검토된 코드의 판"이 2개라는 뜻이 된다.
- 확인 실행이 없으면 2회 뒤의 수정이 독립 리뷰 없이 머지된다. 실행당 pass 비율이 34%이므로 이런 PR이 적지 않다(추론).

## 버린 대안

- 완료 기준의 판을 수정 시각으로 유지하기. 위의 이유로 버렸다.
- 2라운드에서도 항상 전체를 보기. 새 low 지적이 끝없이 나오는 원인이었다.
- 계획 영수증을 트리에 묶고 머지에서 강제하기. 코드를 먼저 쓴 작업이 영수증도 승인도 얻지 못하는 막힌 길이 생겼다. base를 호출자가 주므로 규칙도 약하다.
- 3회차 전체 리뷰. 상한을 3으로 올리는 것과 같다.

## 깨지는 때

- 2라운드의 축소 조건을 잘못 판정해, 검토되지 않은 파일이 변경분만 검토될 때. 그래서 영수증의 `files_reviewed`에 전체로 본 파일과 변경분만 본 파일을 구분해 적는다.
- 확인 실행이 새 결함을 보고도 올리지 못할 때. 범위를 좁힌 대가다. 머지 뒤 수정 커밋의 수로 본다.
- 리뷰어를 고르는 규칙이 후보를 모두 지울 때. `blocked`로 멈추고 사람에게 간다.
- `roles.json`이 깨지거나 없을 때. 리뷰는 돌지 않아야 한다. 조용히 기본값으로 돌면 안 된다.
- 기존 결함을 low로 낮추는 규칙이 완료 기준의 불충족까지 낮출 때. 그래서 불충족은 항상 차단 사유로 둔다.
